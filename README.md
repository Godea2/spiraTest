# Spira Test Set Reconciler

Compare a release-scope workbook with Spira test set membership, decide which cases stay, and remove the rest from their test sets. The browser only talks to this app; the app's server calls the Spira REST API (v7.0) with credentials held in its environment.

Built with Next.js (App Router), TypeScript, React and Tailwind CSS.

## Setup

1. `npm install`
2. Copy `.env.example` to `.env.local` and fill in the values:

   | Name | Purpose |
   | --- | --- |
   | `APP_PASSWORD` | Team password for the sign-in page |
   | `SESSION_SECRET` | At least 16 characters; signs the session cookie and comparisons |
   | `SPIRA_BASE_URL` | Spira site URL, e.g. `https://yourcompany.spiraservice.net` |
   | `SPIRA_USERNAME` | Spira user the server acts as |
   | `SPIRA_API_KEY` | That user's API key (RSS token), including the `{ }` braces |
   | `GEMINI_API_KEY` | Optional. Google Gemini API key for the AI review of blocked cases and the defect finder |
   | `GEMINI_MODEL` | Optional. Gemini model for both; defaults to `gemini-3.8-flash` |
   | `GEMINI_FALLBACK_MODEL` | Optional. Models asked in turn when the main one is busy, fails or is slow (comma-separated, up to 3); defaults to `gemini-3.6-flash,gemini-3.5-flash-lite`, `off` turns them off |

   Sign-in is disabled until `APP_PASSWORD` and `SESSION_SECRET` are set. Comparisons are disabled until all three Spira values are set. Nothing is preset: in **Settings**, pick the project (listed from Spira) and save. On **Compare**, choose a module and the project's test sets are read from Spira, with those whose name starts with the module (for example `Onboarding-Android`, `Onboarding-IOS`) ticked. The release is optional and only labels drafts; module-to-test-set mappings in Settings are optional overrides.

3. `npm run dev` and open http://localhost:3004.

Use a dedicated Spira service account with access to the project and permission to edit its test sets. The API key is sent as a request header, never in the URL, and is never returned to the browser.

## How it works with Spira

| Step | Spira calls |
| --- | --- |
| Settings | `GET users` and `GET projects` (connection and project list), `GET projects/{p}/releases/{r}` (release label), `GET projects/{p}/test-sets?…&release_id=` (test set picker, paged) |
| Compare | `GET projects/{p}/test-sets/{t}`, `…/test-case-mapping` and `…/test-cases` (read only) |
| Card details | `GET projects/{p}/test-cases/{tc}` and `…/test-steps`, plus the same for linked test cases (read only, when you open a card) |
| Membership check | `GET …/test-case-mapping` |
| Dry run | `GET …/test-case-mapping`; nothing is changed |
| Live apply | `GET …/test-case-mapping`, then `DELETE projects/{p}/test-sets/{t}/test-cases/{test_set_test_case_id}` per case |
| Verify | `GET …/test-case-mapping` |
| Record results | `GET …/test-sets/{t}` and `…/test-cases` (current status), then `POST projects/{p}/test-runs/record` per Blocked or Passed case |
| Undo sign-off | `GET projects/{p}/test-runs/{id}` and `…/automated` (checks the test case and runner name), then `DELETE projects/{p}/test-runs/{id}` |
| Execution status | `GET …/test-case-mapping` and `…/test-cases` per test set; read only |
| Record execution | Per batch of up to 20 cases: `GET …/test-sets/{t}` and `…/test-cases`, one `POST projects/{p}/test-runs/create` (unsaved runs with Spira's steps) and one `PUT projects/{p}/test-runs` saving them all with the step results. If Spira rejects the batch, each run is saved on its own. `POST …/test-runs/record` when Spira gives a case no steps. Afterwards `GET …/test-cases` (what Spira now shows) and `GET`/`PUT projects/{p}/test-sets` to keep the test set's status, owner and planned date |
| Test set status | `GET projects/{p}/test-sets/{t}`, then `PUT projects/{p}/test-sets` with the status Spira should show (only when you click **Set to In Progress in Spira**) |
| Undo an execution result | `GET projects/{p}/test-runs/{id}` (checks the test case), then `…/manual` (checks the app's signature in a step) or `…/automated` (checks the runner name), then `DELETE projects/{p}/test-runs/{id}` |
| Defect search | `GET projects/{p}/test-cases/{tc}` and `…/test-steps` for each likely case (read only); `GET projects/{p}` and `GET project-templates/{t}/incidents/types`, `…/priorities`, `…/severities` and `GET project-templates/{t}/test-cases/statuses` for the defect form (read only) |
| Fail cases for a defect | The same calls as Record execution, then `GET projects/{p}/test-runs/{id}/manual` per run (checks the app's signature and finds the Failed step) and one `POST projects/{p}/incidents` linked to those run steps |
| Add a defect as a new test case | `GET projects/{p}/test-cases/{tc}` (folder of the test set's first case), `POST projects/{p}/test-cases`, `POST projects/{p}/test-cases/{tc}/test-steps` per step, `POST projects/{p}/test-sets/{ts}/test-case-mapping/{tc}` per test set, then a comparison of each of those test sets; on a failure, `DELETE …/test-sets/{ts}/test-cases/{tstc}` and `DELETE projects/{p}/test-cases/{tc}` for what was created |
| Undo a defect | `GET projects/{p}/incidents/{id}` (checks the app's signature), `DELETE projects/{p}/incidents/{id}`, then the run undo above for each of its runs; for a case it created, `GET projects/{p}/test-cases/{tc}` (checks the app's signature), `DELETE projects/{p}/test-cases/{tc}` and its test set memberships, then a comparison of those test sets |
| Push to the other platform | Compare and live apply as above for the other platform's test sets; `GET …/test-case-mapping`, then `POST projects/{p}/test-sets/{ts}/test-case-mapping/{tc}` per case to add; `GET projects/{p}/test-runs/{id}/manual` per non-passed source run (read only) and `GET projects/{p}/incidents/search-by-test-case/{tc}` for cases with no defect logged here (read only); then Record execution as above |
| Reports | `GET projects/{p}`, `POST projects/{p}/releases/search` (empty filter, read only), `GET projects/{p}/test-set-folders`, `GET projects/{p}/test-sets?…` and `GET projects/{p}/test-set-folders/{f}/test-sets?…` per folder (paged); `GET projects/{p}/test-sets/{t}/test-cases` per test set in the scope and baseline; `GET projects/{p}/incidents/search?…` (paged, falling back to `GET projects/{p}/incidents`); `GET projects/{p}/incidents/search-by-test-case/{tc}` for failed, blocked and caution cases. All read only |

Live apply removes a test case from a test set; the test case itself is never deleted. Before each batch the server re-reads the test set and only removes memberships that still point at the reviewed test case. Reads are retried on temporary errors; removals and recorded results are never retried automatically, so a failed case is retried only when you choose to.

Opening **Review & apply** reads each test set's membership from Spira (read only, also on **Check Spira again** and before every run). Out of Scope cases that are already gone from Spira, for example removed by an earlier run that reported an error, are counted as removed, so the remove figure only counts what is still in Spira. Any other difference (cases added in Spira, or In Scope and Blocked cases removed outside the app) is listed and blocks live apply until the board is recompared.

Once a live apply is verified (Spira matches the reviewed board), the draft moves from **Drafts** to **Completed**. A draft applied with errors stays under Drafts until a retry succeeds. Completed drafts can still be opened, and their board and review work as before.

A draft with nothing to change in Spira does not need a live apply. That is a draft where every test set is compared, nothing is in Needs Review, and no Out of Scope case is left to remove (none were found, or they were already removed in Spira). The app reads the test sets' membership from Spira (read-only, nothing is written) and, if it still matches the board, moves the draft to Completed with a **No changes needed** badge. This check runs on its own:

- when a comparison finishes;
- after a recompare on the board;
- when the review page opens;
- after a live run that only recorded Blocked or Passed results;
- when **Drafts** or **Completed** opens, for any draft that is ready. Each version of a draft is checked once per browser session, two at a time.

Boards and draft cards also have a **Move to Completed** button. If Spira has changed since the comparison, the draft stays under Drafts and the card says what differs, so the board can be recompared. Blocked results can still be recorded from **Review** after the draft is completed. A completed draft goes back to **Drafts** when its board asks for changes in Spira again: a card moved to Out of Scope or Needs Review, or a recompare that finds new cases to review.

### Test execution

From **Completed**, **Run execution** lists the draft's In Scope cases (including those in Defects) with their latest result, read from Spira when the page opens (and on **Check Spira again**), so results recorded by others show up too. Cases are grouped in buckets with counts: the page opens on **To run**, and a case leaves it as soon as it has a result and shows under Passed, Failed, Blocked or Caution (**All** shows everything). Next and previous in the runner follow the list as it was when the case was opened, so cases leaving the bucket do not shift the order.

- **Run** opens a case step by step: its steps come from Spira (steps of linked test cases are listed in place), and each step is marked Passed, Failed, Blocked, Caution or N/A, with the actual result for anything that did not pass. Keys P, F, B, C and N mark the current step; Ctrl+Enter saves and opens the next case. The case result follows from the steps: the first Failed, Blocked or Caution step decides it, so a tester can stop at a failure. Marks are kept in the draft until saved.
- **Run all** goes through every listed case (or **Run N selected**, the ticked ones) in the runner, one after another: **Save & next** moves on, and the last case offers **Save & finish**. It starts at the first case that has no result or is in progress, and the arrows move back and forth within the run.
- **Pass** records a Passed result with every step passed in one click, with an Undo in the notification. Select several cases and pick a result from the **Mark N as** menu (keys P, F, B, C while it is open). Passed records straight away with every step passed; Failed, Blocked or Caution ask for one reason (Ctrl+Enter records), which goes on the first step while the other steps stay Not Run. Cases are sent 20 per request with a live progress bar and a **Stop** between batches; afterwards Spira is read again and the summary says how many it now shows with that result, with **Retry** for any that failed.
- **Report** downloads an Excel execution report: a summary per test set (executed, passed, failed, blocked, caution, not run, pass rate), every In Scope case with its status in Spira and last run, and every run recorded here with a link to it in Spira.
- A result that is not Passed needs the actual result on that step, or a comment.

Saving records a manual test run in Spira against the draft's release (or the test set's release), the same kind of run Spira's own execution screen saves: each step has its status and actual result, and steps not reached stay Not Run. The comment and the tester's name are added to the actual result of the step that decided the result (the last step for a pass). Spira lays out the run's steps itself; the marks are matched to them by test step, and if Spira's steps would give a different result (the test case changed since it was opened), nothing is saved and the case asks to be marked again. A case with no steps in Spira is recorded as an automated run with the report in its details. The server only records In Scope cases of a verified board, and re-reads the test set first, so a case that left the test set or changed is not recorded. A case can be executed again; Spira keeps every run and shows the latest. Runs recorded here are listed on the case and can be undone, which deletes only runs this app recorded.

Spira marks a test set Completed as soon as runs are saved against it, and clears its owner and planned date. After each recording the app reads the test set again and puts it back: In Progress while any In Scope case is still Not Run, Completed once every case has a result (or is N/A), with the owner and planned date it had before. A test set set to Blocked or Deferred in Spira is left alone. When the page finds a test set Spira shows with the wrong status (for example from a recording made before this upkeep), it shows a warning with **Set to In Progress in Spira**. An owner or planned date Spira already cleared cannot be recovered and has to be set again in Spira.

### Push to the other platform

iOS and Android test sets hold the same Spira test cases, so a module run on one platform can be brought across to the other. A completed draft whose test sets are all iOS (or all Android) has **Push to Android** (or **Push to iOS**) on its card under **Completed**. The page walks through three steps:

1. **Choose the test sets**: each test set is paired with the other platform's test set for the same module (`Payments-iOS` with `Payments-Android`), in the same release first; any other test set can be picked instead. **Compare** creates a draft for those test sets, marked **From iOS**, with the same workbook rows, compares them (read only), and moves every card where the source board has it: a case the source keeps stays in the same column (In Scope, Defects or Blocked), and every other case goes to Out of Scope. A case held twice is matched as often as the source keeps it.
2. **Match the test cases**: the page shows what stays, what is removed and what is added. Cases the source keeps that the other platform lacks (for example test cases created for defects) are listed, and **Add in Spira** adds them after a confirmation, one at a time and never retried. The server checks both boards' signatures, that each case is kept on the source test set, and the test set's membership in Spira now, so a case already there is skipped; the test set is then compared again so the new memberships come from Spira. The removals go through the usual **Review & apply**, with its membership check, dry run and the live apply that asks for the module name; Blocked cases can be signed off there. If the source board changes later, **Match again** moves the cards to match it (a board edit only).
3. **Copy the results**: once the draft is completed, both platforms' results are read from Spira (read only). Each executed case without a result takes the latest result its source case shows: Passed, Failed, Blocked or Caution. A non-passed case recorded here is copied step by step from its source run (statuses and actual results, without the first tester's note); otherwise the result goes on its own. Every run says where it came from ("Same result as on iOS: Payments-iOS (TX:126), test run TR:4567. Defect: IN:264."), naming the defects logged here for the source case or, failing that, the open incidents Spira links to it. Cases that already have a result, and cases not run on the source yet, are left alone. Recording asks for the tester's name, a tick confirming the cases were run on the other platform with the same results, and a confirmation; it runs in batches of 20 with a progress bar and **Stop**, and cases that fail can be retried with the result only. The runs are dated when they are recorded, and can be undone from the other platform's execution page.

### Defects

**Defects** in the menu (also **Find defects** on a board and on the execute page) turns a defect described in plain words into failed runs and one Spira incident, across modules. A defect is not tied to one module: a broken login or balance shows up in Onboarding, Home Screen, Accounts and Transactions alike, so any compared module of the Spira project can be searched, Draft or Completed; you choose which.

Defects can be found before Out of Scope cases are removed. On a draft, every case is searched, including Out of Scope and Needs Review; on a completed module, only the cases still in Spira (In Scope, Defects and Blocked). A case on two drafts (for example a duplicate) is searched once, and a membership removed by a live apply is never offered.

Every board has a **Defects** column (key 5) between In Scope and Blocked. It counts as In Scope: live apply keeps its cases in the test set, the execute page runs them (with a Defect badge), and sign-off never passes them. A case failed for a defect moves to Defects on its board, whichever column it was in, as one step in the board's change history; so an Out of Scope case with a defect is kept and reported as Failed instead of being removed. Like any board move, this asks for a fresh membership check before a live apply. Cards can also be moved to Defects by hand.

With a Gemini key:

1. **Describe it**: name the screen, the action and what happened (Ctrl+Enter searches), and choose the modules the defect is likely in under **Where to look** (**All** and **None** help; the choice is remembered in this browser, and a module opened from its board is always included). Fewer modules make a faster, sharper search.
2. **Understand it**: one quick request, before any case is looked at. Gemini works out the feature or journey the defect is in ("unable to buy airtime" is *Airtime purchase*), the other names testers and case authors use for it and what is part of it (*top-up*, *recharge*, *network provider*, *airtime receipt*), and a bug report reading: title, area, symptom, what should happen and a suggested severity. It sees the modules' and test sets' names, to know how the app is organised. When the description is too vague it asks one question to add before searching again. The page shows the feature and its other names.
3. **Match by context**: Gemini reads the case names (with their test set and workbook scenario), up to 500 per request, so most searches need one request, and picks up to 24 cases that are about that feature: the feature itself under any name, journeys where it is a real step, and results that only exist when it works. Cases of other features are left out even when they share a word, and when the defect is in a step almost every case starts with (signing in, choosing an account), only the cases about that step are picked, not every case that begins with it. Only ids and a relevance come back, so the request is quick. A part that could not be read is reported with a **Search again** button rather than dropped silently. Beyond 2,000 cases, the search is narrowed by the feature's wording first.
4. **Check the steps**: the app reads each picked case's steps from Spira, and Gemini checks them against the defect, 4 cases per request with up to six requests at a time; reading and checking overlap (a batch is checked as soon as its steps are in), and verdicts show on the page as each batch answers, while failing waits until every case is checked. Verdicts: fails, might be affected, or not affected, with the step where the tester meets the defect, a short quote from the case as evidence and a one-sentence reason. It judges by what the steps make the tester do and see, not by shared words, and a case whose steps never reach the broken behaviour is not affected. A search is a handful of Gemini requests in all (one to understand, reused when the same description is searched again in this session; usually one to match; a few small step checks side by side), each with Gemini's light thinking level, so results usually show within a few tens of seconds; the page shows the time as it goes. Each model has its own capacity, so when the main model is busy ("high demand"), fails, or has not answered in time (10 seconds to understand, 18 to match, 20 otherwise), the server asks the next fallback model (`GEMINI_FALLBACK_MODEL`: Gemini 3.6 Flash, then 3.5 Flash-Lite, through Gemini's other endpoint) at once, uses the first valid answer and cancels the rest; only the last model retries a busy answer. When every model was busy, the page waits a few seconds and asks once more. If Gemini still cannot work out the feature or match the cases, the search does not stop with an error: it says why (naming each model and why it failed), offers **Search again**, and drafts the defect as a new test case (or lets you write it yourself) so it can still be created and failed; a case whose steps could not be checked is listed as "might be affected". The server logs how long each Gemini request took, which model answered and Gemini's error (never the content), so a slow step can be found in the Vercel logs. An error says which step did not finish.
5. **Guard against wrong failures**: the server only lets a case count as failing when the step exists, the quote is found word for word in the case, and the confidence is at least medium; anything else is offered as "might be affected" and is not ticked. Only cases that fail are ticked, and each failing step can be changed.
6. **Fail and log**: after a confirmation that lists the cases per module and the cards that change column, each ticked case moves to Defects on its board and gets a manual Failed run (a case that could not be recorded moves back): the steps before the failing step are Passed (or left unmarked, as you choose), the failing step is Failed with your description as its actual result plus "Defect: title" and the tester, and the steps after it stay Not Run. A case without steps is failed as a whole with the description. Then one incident is created with the title, type, severity and priority (from the project's own lists, preset from Gemini's suggestion), the detected release, steps to reproduce taken from the first failed case, and the list of failed cases grouped by module; it is linked to the Failed step of each run in every module, which the server reads back and checks is a run this app recorded for that case. If the description changes after a search, failing is blocked until you search again, so the runs always carry the description the cases were matched to.

**Add the defect as a new test case.** When no case fails (cases that only might be affected do not count), Gemini drafts the test case that would have caught the defect, and with **When no case fails, add the defect as a new test case** on (the default, remembered in this browser) the confirmation to create it, fail it and log the incident (logging is switched on for it) opens as soon as it is drafted, listing each of those steps for a final approval, after a search that read and checked every case (when Gemini could not finish, the draft waits for you instead); nothing is written until you confirm, and editing the draft first stops it from opening on its own. The draft has a name in the style of the test set's cases, a description, the steps with expected results, and the step where it fails. It also picks the test sets it belongs in (one per platform, up to 4), from the modules searched. **Add a new test case** does the same by hand after any search. Everything can be edited before failing, and **Status in Spira** sets the test case's own status from the project's list (for example Ready for Test; "Project default" leaves it to Spira); the last choice is remembered per project in this browser, and its run is Failed either way. **Create & fail** then creates the case in Spira (in the folder of the test set's first case, with the app's signature in its description) with its steps, adds it to each chosen test set, puts the new card on those boards in Defects (so it counts as In Scope, a live apply keeps it, and a completed module stays completed; the server signs each test set again with only that card and its membership added, so no full recompare is needed and a change made in Spira since the last compare still shows in the membership check), and fails it with the other ticked cases under the same incident. If any of these writes fails, what was created is removed again. **Undo** on the defect also deletes the created case, once none of its runs are left, after checking it carries the app's signature, and takes its card off the boards the same way. The Spira user of `SPIRA_API_KEY` needs permission to create test cases and change test sets.

**No duplicates.** A case a defect already failed cannot be failed again: in the results it is shown unticked and locked with the defect that failed it (and its incident), and the app refuses it even if asked, until that defect is undone. A case that is Failed in Spira now (for example by another tester) is not ticked either; tick it only for a different defect. While you type, a description that reads like a defect already raised in this project shows that defect, with its failed cases, incident and created test case; the confirmation then never opens on its own, and a new test case for it is blocked until you say **It's a different defect**. A new test case is also blocked when a case in its test sets, or one created for an earlier defect, already has the same name (nearly word for word: "MTN is listed" and "Glo is listed" are different), so you fail that case instead or rename this one. The list of defects is kept in this browser, so on another browser the Failed status from Spira is the guard.

**Defects found** lists each defect of the project, newest first, with its modules, a link to its incident in Spira, and its cases (module, failing step, the column it came from, and its run). It can be filtered by module. **Log in Spira** retries an incident that could not be created, and **Undo** deletes the incident and the defect's runs (each checked to be this app's) and moves each card back to the column it came from, unless another defect still holds it; the cases then show their previous result. The list is kept in this browser, like drafts; defects kept inside a draft by an earlier version move to it when the page first opens. Searching changes nothing in Spira; only failing and logging write, and neither is retried automatically. Only case names, workbook scenarios, steps and the defect description are sent to Google, with storage turned off.

### Reports

**Reports** builds an executive SIT report straight from Spira, laid out like the daily SIT test report: a status pill, headline figures, module tables, exit criteria, defects and a QA assessment. Nothing in it comes from drafts or this browser's data; every figure is read from Spira when you click **Generate report**, and nothing is written.

- **In scope** is the release being tested (for example 1.0.0.0002) and **Baseline** is the release that holds every case across all modules and platforms (for example 1.0.0.0001). Each includes its sprints, and can be narrowed to a test set folder and its subfolders (for example SIT Cycle 2). The scope starts at the release chosen in Settings, and the baseline at the release before it. The baseline is optional. Each release and folder in the lists shows how many test sets it would give with the other choice, and a release and folder with no test sets in common says which releases that folder's test sets are planned for and which folders hold that release's test sets, with a button for each.
- A test set belongs to a module and platform by its name (`Onboarding-IOS`, `Payments - Android`), or by the module mappings in Settings when set. Test sets whose name or folder mentions API are the API stream. A test case counts once per module, however many platforms it is on; its result across platforms is the worst one (Failed, then Blocked, Not Run, Caution, Passed).
- Executed is Passed, Failed, Blocked or Caution. Execution % is executed out of the cases in scope (N/A cases excluded), and the pass rate is passed out of executed.
- Defects are the incidents detected in the scoped release (or its sprints) plus those linked to scoped cases. They are shown by severity and age, by priority, by retest state, and in a register with links to Spira.
- Seven exit criteria (execution and pass rate against their targets, no blocked cases, no open Critical or High defects, all defects closed, no defect older than the ageing limit, every module fully run) decide the automatic status: Green when all are met, Red with an open Critical defect, a pass rate more than 10 points under target, or go-live three days away or less, otherwise Amber. The status can be set by hand.
- Each module is Ready, At risk, In progress or Not started, with the reason. **Baseline vs scope** shows, per module and platform, the cases in the baseline, in scope, added and deferred.
- **Data checks** flag what would make the figures wrong: failed results with no linked defect, test sets whose counts in Spira differ from their cases, defects without severity or priority, test sets past their planned date, results that differ between platforms, and cases on only one mobile platform.
- **Change since the last report** compares with the last report generated in this browser on an earlier day (one snapshot a day is kept per project and scope, in `localStorage`).

Title, cycle, prepared by, go-live date, targets, status and QA notes update the report at once; a different scope or baseline needs **Generate report** again. **Print or save PDF** prints the report on A4 landscape pages, and **Excel** downloads every table. Spira's results are read 10 test sets at a time, and defect links are looked up for at most 400 failed, blocked or caution cases; the report says when that limit was reached.

### Blocked cases and sign-off

On the board, **Not implemented yet** has one keyword list per test set in the draft (for example `nin, bvn, google` for Onboarding-IOS). Only the **test scenario** is searched: the Spira test case name and the Test Scenario cell of the workbook row it matched. Test steps and test data are deliberately ignored, because a step that enters a BVN does not make a case depend on BVN verification. Keywords match whole words and their plural, ignoring case, so `nin` matches `NIN` and `BVN/NIN` but not `running`.

**Filter** collects the In Scope and Blocked cases whose scenario mentions a keyword of their test set. If `GEMINI_API_KEY` is set, the server asks Gemini whether each case really depends on the missing feature, and gets back a verdict, a confidence and a one-sentence reason. For example, "Verify no sensitive data (BVN, passcode) is logged" is about logging, so it is not blocked. A case that has to go through the missing feature's path to reach what it checks (for example "the Account number step is never shown to new customers, who use BVN/NIN instead") counts as blocked, usually with medium confidence. Without a key, a keyword in the scenario counts as Blocked. Only test case names, workbook scenarios and keywords are sent to Google for this review, with storage turned off; Spira is not called. Cases go in batches of 20, and each request gives up with a clear message after 50 seconds; answers already received are kept, and **Stop** ends a long run early.

**Deep check** (with a Gemini key) asks about the In Scope and Blocked cases whose scenario names none of the keywords, in case the wording describes a missing feature another way. Its suggestions are marked "Deep check" with the features the AI named. A deep-check verdict is redone when the test set's keywords change.

Nothing moves on its own. The review lists the suggested changes: cases to move to Blocked, and cases to move back to In Scope, including Blocked cases whose scenario mentions none of the keywords. Confident suggestions are ticked; low-confidence answers and cases with no keyword are left unticked for you to decide. **Apply** moves the ticked cases in one step, which is in the change history and can be undone. Verdicts are saved in the draft, so filtering again only sends new or changed cases unless you choose **Re-analyse all**. A table shows, for every keyword, how many cases mention it in each column, so a keyword found only in Out of Scope cases shows that the workbook left those cases out.

Click a card (or focus it and press Enter) to open its details: where it sits and why, the not-implemented verdict, the matched workbook row with all its cells (test steps, test data, expected results), and the test case as stored in Spira, with its description, properties and test steps, including steps from linked test cases. Use the arrow keys to move through the column and Esc to close. Ctrl-click or Shift-click selects cards instead. On desktop, the sidebar collapses to icons (button at the top, or Ctrl+B) to give the board more room.

On **Review & apply**, a live apply removes Out of Scope cases, then records an automated test run with status **Blocked** for each Blocked case. Ticking **Also mark In Scope cases as Passed** (off by default, with its own confirmation) records **Passed** runs for In Scope cases too. Runs use the draft's release, or the test set's release when the draft has none. Cases that already have a result in Spira are skipped and listed. The IDs of recorded runs are kept in the draft so **Undo sign-off** can delete exactly those runs.

### Matching rules

For each test case in a test set:

1. If a workbook **TC ID** (for example `TC-ONB-001`) appears in the test case name or in one of its custom property values, it matches that row. Separators and case are ignored, so `TC ONB 001` matches too, but `TC-ONB-0010` does not.
2. Otherwise, if the test case name equals a workbook **Test Scenario** (ignoring case and punctuation), it matches that row.
3. A match on the In-Scope sheet suggests **In Scope**; on the Needs Confirmation sheet, or on several different rows, **Needs Review**.
4. No match suggests **Out of Scope**, unless the name closely resembles a scenario, in which case it goes to **Needs Review** for a person to check.

Workbook rows that no test case matched are listed as missing from Spira.

## Storage

There is no database. Settings, drafts and the activity log are kept in the browser's `localStorage`, so each browser (and each domain, including Vercel preview URLs) has its own drafts.

The server is stateless. It signs every comparison and passing membership check with `SESSION_SECRET` and re-verifies those signatures before a membership check, apply or verify, so suggestions edited in the browser are rejected. The membership check also covers the reviewed decisions, so changing a decision requires a new check.

## Deploying to Vercel

Set `APP_PASSWORD`, `SESSION_SECRET`, `SPIRA_BASE_URL`, `SPIRA_USERNAME` and `SPIRA_API_KEY` (and optionally `GEMINI_API_KEY`, `GEMINI_MODEL` and `GEMINI_FALLBACK_MODEL`) under **Settings → Environment Variables** (`.env.local` is not deployed), then redeploy. If your Spira instance restricts access by IP address, it must allow Vercel's outbound traffic.
